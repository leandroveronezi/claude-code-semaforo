# CLAUDE.md

Guia de orientação para trabalhar com código neste repositório.

## O Projeto

**Semáforo de Status** — painel flutuante PyQt6 (Linux, com suporte a Windows validado numa máquina real — ver `pty_session_windows.py`; detecção de foreground pra supressão de alerta continua X11-only, ver abaixo) que mostra um mini semáforo (🔴🟡🟢) por sessão monitorada, mais um mascote animado único que reflete o estado agregado de todas as sessões. Integração pronta com Claude Code via hooks, então cada sessão do Claude vira uma coluna automaticamente.

**Convenção:** toda documentação e comentários visíveis ao usuário estão em pt-BR; siga essa convenção também nos comentários de código.

## Comandos

```bash
pip install -r requirements.txt        # PyQt6==6.6.1 / PyQt6-Qt6==6.6.3 pinned se wheels falharem
python3 main.py                        # rodar app (ícone de bandeja aparece imediatamente)
python3 simulate.py                    # 3 sessões fictícias alternando status, para teste
python3 status_writer.py <id> <idle|working|error> --label "..." --message "..."   # reportar sessão manualmente
python3 autostart.py {install|remove|status}   # entrada freedesktop.org autostart
python3 hooks/install.py               # (re)instalar hooks do Claude Code em ~/.claude/settings.json (idempotente)
```

Não há test suite, linter ou build step configurado neste projeto.

`SEMAFORO_STATUS_DIR` — variável de ambiente que override o diretório de sessões (padrão `sessions/` ao lado de `status_store.py`). Necessária se rodar múltiplas instâncias compartilhando estado.

`SEMAFORO_DEBUG=1` — sobe o nível de log (ver `logging_setup.py`) de INFO para DEBUG.

## Arquitetura

**Sessões são arquivos, não conexões.** A superfície de integração inteira é `sessions/<session_id>.json`, escrito atomicamente via `status_store.write_status()` (temp-file + `os.replace`, com retry curto pra `PermissionError` — `_replace_with_retry` — porque no Windows o `MoveFileEx` por trás falha enquanto outro processo, tipicamente a sync engine do OneDrive ou o próprio `QFileSystemWatcher` do app, tem o destino aberto sem `FILE_SHARE_DELETE`; no POSIX o `rename(2)` nunca falha assim e o retry não chega a disparar). `SessionManager` (`session_manager.py`) monitora esse diretório com `QFileSystemWatcher` (+ poll de 2s como fallback, pois atomic renames às vezes dropa a watch) e deriva tudo do que lê: status, label, message, activity, pid_chain, updated_at. Qualquer processo, em qualquer linguagem, pode dirigir o painel apenas escrevendo esse shape JSON; `status_writer.py` é a wrapper CLI de conveniência.

**Integração Claude Code é um hook script, não um plugin.** `hooks/status_hook.py` é invocado pelo Claude Code (configurado em `~/.claude/settings.json` ao nível de usuário, instalado/mesclado por `hooks/install.py`) em eventos do ciclo de vida (SessionStart, UserPromptSubmit, PreToolUse/PostToolUse, Notification, PermissionRequest, Stop, SessionEnd, etc. — veja `MANAGED_HOOKS` em `hooks/install.py`). Mapeia cada evento a um status (idle/working/error/remove), extrai melhor-esforço uma preview para o balão do mascote (da transcript em `Stop`, ou do payload de permissão/notificação pendente), e chama `write_status`/`remove_status`. Como `~/.claude/settings.json` fica fora deste repo, `main.py` confere `is_up_to_date()` a cada início e reinstala silenciosamente se os caminhos do hook ficarem velhos (ex.: pasta do projeto movida/renomeada) — é por isso que comandos de hook terminam em `|| true` e nunca bloqueiam o Claude Code mesmo se este app quebrar.

**Um painel, um mascote — não uma janela por sessão.** `SemaphorePanel` (`semaphore_panel.py`) é um widget flutuante único que layout uma `LightColumn` (`light_column.py`) por sessão lado a lado. `MascotOverlay` (`mascot_overlay.py`) é uma janela *separada* always-on-top que segura um `MascotWidget` (`mascot.py`) + `SpeechBubble` (`speech_bubble.py`) compartilhados; reflete o estado *agregado* de todas as sessões (prioridade error > working > idle, igual ao ícone da bandeja) e reveza entre múltiplas sessões do mesmo tier em timer, pausando ao passar o mouse. Transições idle são notificações enfileiradas one-shot (sessão terminando não fica loopando forever) que se intercalam em uma rotação error/working em andamento em vez de ficarem travadas atrás — veja `_combined_entries` / `IDLE_DONE_MARKER` em `mascot_overlay.py` para a mecânica exata antes de tocar lógica de rotação.

**Engine de animação do mascote é um port fiel de clippy.js.** O frame engine de `mascot.py` (`_step`, `_get_next_frame_index`, branching, `exitBranch`, `useExitBranching`) é um port direto de `clippy.js/src/animator.js`, não uma simplificação — preserva branching de animação probabilístico e frames compostos multi-imagem. `assets/mascot/<Name>/agent.json` é regenerado de `clippy.js/agents/<Name>/agent.js` via `scripts/import_mascot_agents.py` (curates `status_animations` por-character já que clippy.js não tem noção de idle/working/error); sons `.wav` são extraídos on-demand via `scripts/import_mascot_sounds.py` (precisa de `ffmpeg`). Não edite `agent.json` manualmente — corrija o importer e rerun. Assets do mascote são sprites originais Microsoft redistribuídos pela comunidade clippy.js sem licença clara — trate como uso pessoal/local apenas, não para redistribuição.

**Detecção de foreground é X11-only e falha aberto para "alert".** `foreground.py`'s `active_window_pid()` shell-outa para `xprop`; em Wayland ou sem `xprop` retorna `None`, e todo caller deve tratar como "unknown" (i.e. ainda alert) em vez de assumir foreground. Usado para suprimir beep/notificação de erro quando o usuário já está olhando para a sessão em questão — matched via `ancestor_pids()` (caminha `/proc/<pid>/stat`) registrado em `pid_chain` de cada sessão.

**Limpeza de sessão stale** vive em `SessionManager._check_stale`: sessões working/error intocadas por 10+ minutos revert para idle (provável processo morto, não alerta real); qualquer sessão intocada por 4+ horas é removida inteiramente. Sessões idle nunca são auto-removidas por idade apenas.

**Cota da conta (Session 5h / Weekly 7d) é raspada da tela, não de uma API.** Não existe hook, arquivo local nem API pública para os números que `/usage` mostra no CLI — é dado exclusivo daquela tela interativa (o próprio binário do `claude` busca isso de um endpoint OAuth interno não documentado). `account_usage.py` automatiza a tela em vez de reimplementar esse endpoint: abre um `claude` real num pseudo-terminal (backend por SO, ver parágrafo seguinte), digita `/usage` e usa `pyte` pra renderizar e ler o texto igual um humano veria. Dois efeitos colaterais são neutralizados deliberadamente: `SEMAFORO_SKIP_HOOK=1` no ambiente do processo filho (checado logo no início de `hooks/status_hook.py` e `hooks/statusline_hook.py`) pra essa sessão descartável não virar uma coluna fantasma no painel; e um `--session-id` fixo (`FIXED_SESSION_ID`) cujo `.jsonl` é apagado ao final, pra não acumular sessões vazias no `/resume`. `SessionManager` chama `fetch_account_usage()` (bloqueante, ~15-30s) numa `_AccountUsageThread` no intervalo `Config.account_usage_poll_minutes` (editável nas configurações, padrão 5min — ver `_account_usage_poll_ms`), mais um debounce igual no gatilho disparado pelo hook `Stop` de cada sessão, e mostra o resultado no tooltip da bandeja. `_poll_account_usage` recusa disparar se já existe uma `_account_usage_thread` em andamento, então nunca há duas consultas simultâneas *dentro do mesmo processo*; entre *processos* diferentes (rodar `python3 account_usage.py` manualmente pra depurar enquanto o app já está de pé, ou duas instâncias do app — ver `SEMAFORO_STATUS_DIR` acima para o caso análogo de `sessions/`), quem fecha a lacuna é `_try_acquire_account_usage_lock()` em `fetch_account_usage()`: uma trava de SO (`flock`/`LockFileEx`, via `ACCOUNT_USAGE_LOCK_PATH`) não-bloqueante sobre o file descriptor — se outro processo já a detém, desiste na hora em vez de esperar, e como é do SO sobre o fd (não lockfile-com-pid), libera sozinha mesmo se o processo morrer (SIGKILL incluso), sem lock obsoleto pra limpar. Sem essa trava, dois processos sobem o mesmo `--session-id` fixo em paralelo — reproduzido de propósito uma vez, corrompeu `~/.claude.json` de verdade (ver backup/restore no parágrafo seguinte, que continua como segunda camada de proteção). `_AccountUsageThread` **sobrescreve `QThread.run()` diretamente** em vez do padrão comum `moveToThread()` + `started`/`quit()` — esse padrão tem uma corrida real do Qt quando o trabalho conectado a `started()` é síncrono/direto: como `finished` é emitido cross-thread, o `quit()` conectado a ele fica enfileirado pra rodar na thread principal, e pode chegar antes do `exec()` da thread em background sequer ter começado — nesse caso `quit()` vira no-op, a thread fica presa num loop de eventos vazio pra sempre (`isRunning()` nunca volta a `False`), e quando o Python por fim coleta o `QThread` órfão, o destructor do Qt aborta o processo com "QThread: Destroyed while thread is still running". Isso não é teórico: reproduzido de forma 100% determinística (~1s depois de toda consulta bem-sucedida) antes da reescrita. Sobrescrever `run()` evita o problema inteiro (quando `run()` retorna, a thread já está oficialmente terminada). `_wait_for_account_usage_thread`, ligado a `aboutToQuit`, só dá `wait()` (sem `quit()`, que não faz sentido pra uma thread sem `exec()`) pra não deixar o app fechar com a thread ainda rodando. Consultas em sequência rápida parecem ser limitadas pelo servidor (o "% used" da sessão às vezes não carrega, o da semana sim) — por isso o parser em `_parse_usage_screen` trata os dois blocos como opcionais independentes em vez de exigir os dois.

**O backend do pseudo-terminal é por SO, e o Windows exige mais cautela que o Linux.** `pty_session_posix.py` (`pty.fork`, testado rodando de verdade) e `pty_session_windows.py` (ConPTY via `pywinpty`, validado numa máquina Windows real — ver contrato comum `write`/`read_into`/`terminate` no cabeçalho do arquivo) são escolhidos por `IS_WINDOWS` e importados só dentro de `fetch_account_usage()`, nunca no topo do módulo: `session_manager.py` importa `account_usage` no nível de módulo, então um import incondicional do backend errado (ou de uma dependência ausente, como `pywinpty` não instalado) derrubaria o app inteiro em vez de só desabilitar essa consulta. Antes de digitar qualquer coisa na tela, o texto inicial é checado contra `ONBOARDING_RE` (telas de primeira execução do CLI — escolha de tema, escolha de método de login): atravessá-las às cegas mandando `\r` viraria "selecionar opção 1" no menu de login, disparando um fluxo OAuth de verdade (abre navegador, espera código colado) em nome do usuário sem ele ter pedido nada — melhor reconhecer e desistir. No Windows, `_claude_bin()` procura em mais lugares que só o PATH (instalação via `npm` em `%APPDATA%`, binário embutido na extensão do VS Code em `.vscode(-insiders)/extensions`, já que instalação só-pela-IDE é comum lá), e `_project_hash_dirs()` tenta as duas variações de caixa da letra do drive (`c-` vs `C-`) ao limpar o `.jsonl` da sessão descartável, porque esse nome de diretório em `~/.claude/projects/` é derivado do cwd como string e diverge conforme quem lançou o processo. `~/.claude.json` é config **global** do CLI, não por-sessão — todo `claude` que sobe, inclusive essa sessão descartável, lê/mescla/regrava o arquivo inteiro — e corre risco real de corromper se o processo for morto (SIGKILL, ver `GRACEFUL_EXIT_WAIT_SECONDS`) no meio de uma escrita; como esse arquivo é lido por *todo* `claude` subsequente, uma corrupção aí quebraria o CLI de verdade do usuário, não só essa consulta de cota. `fetch_account_usage()` tira um backup em memória do arquivo antes de abrir a sessão (`_backup_claude_config`) e, no `finally`, só restaura (`_restore_claude_config_if_corrupted`) se o arquivo ficou com JSON inválido — nunca só por ter mudado de conteúdo, pra não apagar uma escrita legítima de uma sessão interativa concorrente (não tenta resolver a corrida de "última escrita ganha" em si, só evitar que o arquivo fique ilegível).

O mesmo dado também aparece visualmente: `AccountUsageBadge` (`account_usage_widget.py`) é uma caixa deitada (duas barras, Sessão 5h / Semana 7d, com % e "reseta ...") desenhada com o mesmo padrão de `LightColumn`/`SpeechBubble` (QPainter direto, sem layout). Fica colada logo abaixo do mascote — `MascotOverlay._relayout()` (`mascot_overlay.py`) trata a janela inteira como "ancorada" em `self._anchor` (posição arrastada do mascote) e recalcula mascote+balão+caixa de cota ao redor dela a cada mudança, então arrastar/salvar posição e o mascote reaparecer depois (`set_visible_animated`) já vêm com o layout certo automaticamente — não existe estado de posição separado pra caixa. A caixa nunca colide com o balão de fala porque o balão só aparece acima ou ao lado do mascote (nunca abaixo); perto da borda inferior da tela a caixa é clampada pra não vazar da tela. Controlada por `Config.account_usage_badge_enabled` (aba Mascote das configurações) — desligar só esconde a caixa, não para as consultas de `fetch_account_usage()` (o tooltip da bandeja continua funcionando).

`Config.mascot_enabled` e `Config.account_usage_badge_enabled` são independentes: desligar "Mostrar mascote" só tira o personagem e o balão de fala da janela (via `MascotOverlay._mascot_enabled`, propagado em `update_config()`) — a caixa de cota, se habilitada e com dado disponível, continua aparecendo sozinha na mesma âncora. Nesse caso `_relayout()` usa um retângulo de referência de tamanho zero na âncora no lugar do mascote (em vez do tamanho real do sprite), então a janela encolhe e a caixa ocupa o lugar onde o mascote estaria, sem deixar vão vazio. `SessionManager._sync_mascot_visibility()` decide a visibilidade da janela inteira como `want_mascot or want_badge` (cada um checado contra `mascot_overlay.has_badge_content` / sessões ativas / oculto manualmente), então a janela some só quando nenhum dos dois tem o que mostrar.

**Aviso de nova versão é git-pull, não auto-update.** Não há instalador nem pacote — o app é consumido via `git clone`/`git pull` manual, então não existe como empurrar update nenhum; só dá pra avisar. `version.py` guarda `__version__` local (bump manual a cada release + tag no GitHub correspondente); `update_checker.py`'s `fetch_latest_release()` consulta `GET /repos/leandroveronezi/claude-code-semaforo/releases/latest` (stdlib `urllib`, sem dependência nova) e `is_newer()` compara semver — qualquer falha (sem rede, rate limit, repo ainda sem nenhuma release) devolve `None` silenciosamente, nunca interrompe o app. `SessionManager` roda essa consulta numa `_UpdateCheckThread` (mesmo motivo do `run()` sobrescrito de `_AccountUsageThread`, ver comentário acima — aqui a corrida nem chegaria a se manifestar já que não há `exec()` nenhum rodando, mas o padrão é mantido por consistência) disparada de `_scan()` na transição de 0 pra N sessões monitoradas (painel/mascote "abrindo"), não em timer solto — é o momento em que faz sentido interromper o usuário com esse tipo de aviso informativo. Debounce de 6h (`UPDATE_CHECK_MIN_INTERVAL_SECONDS`) evita bater no GitHub toda vez que sessões abrem/fecham ao longo do dia. Canal único (nunca os dois, diferente dos avisos de cota/tokens que sempre disparam nos dois): balão do mascote via `mascot_overlay.enqueue_idle()` se `MascotOverlay.character_visible()` (personagem de fato visível agora, não só a caixa de cota) for `True`; senão `tray.showMessage()` (balão nativo da bandeja, perto do relógio) — clicar nele abre a página da release no navegador. `Config.last_notified_release` persiste a última tag já avisada, pra nunca reavisar a mesma versão entre reinícios do app.

**Config** (`config.py`) é um dataclass único persistido como YAML em `~/.config/semaforo-status/config.yaml`, editável via menu de bandeja `SettingsDialog` (`settings_dialog.py`). `Config.load()` silenciosamente dropa chaves desconhecidas, então arquivos config antigos nunca crasham uma versão mais nova do app.

**Log é arquivo rotativo, não best-effort silencioso.** `logging_setup.py` expõe `setup_logging(logger_name, filename)`, chamado por qualquer módulo que precise logar (idempotente — múltiplas chamadas com o mesmo `logger_name` no mesmo processo reusam o handler já criado, sem duplicar linhas). Grava em `~/.config/semaforo-status/logs/`, com `RotatingFileHandler` (1MB × 3 backups = ~4MB de teto por logger) — nunca cresce sem limite. Dois loggers: `"semaforo"` (`semaforo.log`) para o app principal (`main.py`, `session_manager.py`, `account_usage.py`) e `"semaforo.hooks"` (`hooks.log`) para os scripts de hook, apartados porque estes rodam como processo curto a cada evento do Claude Code e podem gerar muito mais entradas que o app em si se algo quebrar. `main.py` também instala `sys.excepthook` pra logar qualquer exceção não tratada que escape do loop de eventos do Qt — sem isso, ela só apareceria em stderr, invisível quando o app sobe via autostart/bandeja sem terminal. Nível padrão é INFO; `SEMAFORO_DEBUG=1` sobe pra DEBUG. Como o comando do hook termina em `|| true` (ver acima) por design — nunca deve bloquear o Claude Code — esse era historicamente o ponto mais silencioso de falha: `hooks/status_hook.py` e `hooks/statusline_hook.py` agora envolvem a chamada de `main()` em try/except só pra logar antes de deixar o erro seguir engolido como sempre.

## Arquivos-Chave

- `status_store.py` — protocolo de sessão em disco (ler/escrever/remover), compartilhado pelo app e qualquer reporter externo
- `session_manager.py` — descoberta de sessão, ícone de bandeja, sweep de sessão stale, reancoragem em mudança de tela
- `mascot_overlay.py` — janela do mascote: layout, engine de rotação/fila, ancoragem multi-monitor
- `mascot.py` — engine de animação/frame derivado de clippy.js
- `hooks/status_hook.py` + `hooks/install.py` — toda a integração Claude Code
- `foreground.py` — detecção de janela foreground X11 para supressão de alerta
- `account_usage.py` — raspagem best-effort da cota de conta (Session 5h / Weekly 7d) via automação de pty do `/usage` do CLI, mais o backup/restore de `~/.claude.json`
- `pty_session_posix.py` / `pty_session_windows.py` — backend por SO do pseudo-terminal usado por `account_usage.py` (`pty.fork` vs ConPTY/`pywinpty`), mesmo contrato `write`/`read_into`/`terminate`
- `account_usage_widget.py` — caixa deitada com a cota da conta, exibida abaixo do mascote
- `logging_setup.py` — logging central com rotação de arquivo (`~/.config/semaforo-status/logs/`), usado pelo app e pelos hooks
- `version.py` — `__version__` local, bump manual a cada release
- `update_checker.py` — consulta best-effort à última release no GitHub, pra avisar sobre versão nova
